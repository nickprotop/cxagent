## Per-tool detail

### Claude Code

- **Rendering glyphs**: `⏺` marks the start of a tool-call line; `⎿` marks the indented tool-result line beneath it. Source: web search result quoting user-facing description of the copy-paste artifact behavior (secondary source, not Anthropic docs) — corroborated by my own direct knowledge of the CLI, flagged as such since I could not find an official doc page stating the glyph meanings explicitly. Confidence: medium (converging secondary source + direct knowledge, no primary doc citation for the glyphs themselves).
- **Collapse/expand mechanism**: `Ctrl+O` toggles between collapsed and expanded tool output for the whole transcript. This is **session-scoped and does not persist** — every new session starts fully expanded. This exact pain point is the subject of two related issues:
  - [#39683 "Persistent output verbosity setting (default collapsed tool output)"](https://github.com/anthropics/claude-code/issues/39683) (closed as duplicate, opened March 2026) — direct user complaint: *"When reviewing a session with 10-20 tool calls, the signal (Claude's analysis and decisions) gets buried in the noise (raw diffs, command output, search results)."* Requests a persistent `settings.json` key `outputVerbosity: "collapsed"`, with a stretch goal of **per-tool** verbosity control (different defaults for Edit/Bash/WebSearch).
  - [#26968 "Truncate or filter large MCP tool results in verbose output"](https://github.com/anthropics/claude-code/issues/26968) (closed as not planned) — complaint specifically about MCP tool payloads (e.g. Playwright `browser_snapshot`) dumping **"hundreds of lines for a simple page, easily 1,000+ for any real web application,"** burying model reasoning and subagent prompts. Proposed fix: auto-truncate to first N lines + a `[truncated]` marker, plus per-MCP-server verbose toggle (citing npm's `DEBUG=namespace:*` as precedent).
- **Full-screen/transcript mode**: `Ctrl+O` also enables a separate alternate-screen "fullscreen rendering" mode (flicker-free, only renders visible messages, supports less-style navigation/search, mouse click-to-expand on tool results). Source: [code.claude.com/docs/en/fullscreen](https://code.claude.com/docs/en/fullscreen).
- **`/focus` command**: switches to "a quiet view showing only the last prompt, a one-line tool-call summary (with diffstats), and the final response" — i.e. an explicit "hide the noise" mode distinct from the default. Source: same fullscreen docs page.
- **Recent change**: the collapsed one-line tool summary now shows a **live elapsed-time counter** for long-running calls "so long-running tool calls visibly tick instead of looking stuck" (per Aug 2026 changelog aggregator). This directly targets finding #6 (progress indicator).
- **Takeaway for cxagent**: Anthropic's own users are asking for exactly what cxagent's team lead is trying to solve — default-collapsed, low-noise tool rendering, with per-tool granularity as a stretch goal. Two independent issues converge on the same ask; both remain unresolved/closed-without-action, suggesting this is a real unmet need in the space, not a solved problem to copy verbatim.

### Gemini CLI

Best-evidenced non-Claude tool in this research, because there's a concrete, merged/in-review PR describing before/after behavior.

- **PR #20974 "feat(cli): implement compact tool output"** ([google-gemini/gemini-cli#20974](https://github.com/google-gemini/gemini-cli/pull/20974)):
  - **Problem stated**: "terminal ergonomics issues where tool outputs consumed excessive vertical space, creating a wide visual gap between user prompts and system responses" — tackles "verbose JSON rendering and lack of output control."
  - **Mechanism**: refactors high-volume tools (`grep`, `ls`, `read_many_files`) to return **structured result objects** rather than raw text, so the renderer can choose a compact representation instead of dumping tool-native output.
  - **New setting**: `ui.compactToolOutput` (default `false` — i.e. opt-in, not the default even after shipping).
  - **Compact rendering**: a `DenseToolMessage` component renders **single-line summaries**: status + description + diff statistics, with interactive expansion.
  - **Grouping**: `ToolGroupMessage` does **segment-based rendering** that "densely packs consecutive compact outputs while isolating standard tools like shell commands in bordered boxes" — i.e., a real grouping/boundary rule: dense (file-op-like) tools get packed tightly together, but shell/exec-type tools still get a bordered block even in compact mode. This is the clearest evidence in the whole research set of a tool explicitly choosing *which* tool types get grouped vs. boxed.
- **Height-rendering caveat**: separate issue notes tool output falls back to raw Markdown (loses formatting) "when any height constraint is present," to avoid flicker — a reminder that compact/height-constrained rendering paths are a known source of regressions industry-wide, not just a cxagent risk.

### OpenAI Codex CLI (codex-rs, Rust TUI)

- **Architecture**: `ChatWidget` (in `codex-rs/tui/src/chatwidget.rs`) consumes protocol events and maintains both **committed transcript cells** (finalized `HistoryCell`s, e.g. `ExecCell`, `McpToolCallCell`) and a single **in-flight `active_cell`** that mutates in place while streaming — described as "often representing a coalesced exec/tool group." Source: GitHub source browse of `chatwidget.rs`.
- **Grouping evidence is partial**: the "coalesced exec/tool group" language implies some grouping happens for the currently-streaming cell, but I could not confirm a persistent visual group header (nothing like Gemini's bordered-box distinction was found in the parts of the source I could inspect).
- **User complaint — [#21252 "Adding CLI Option to hide tool activity"](https://github.com/openai/codex/issues/21252)** (open, no maintainer response found): *"The TUI transcript can become dominated by tool-call cells during long sessions,"* making it hard to review sessions focused on reasoning/final answers. Proposes a `[tui] hide_tool_activity = true` config plus live slash commands (`/tool-activity hide|show|toggle|status`) that would suppress exec/MCP/web-search/image/patch/collaboration tool cells while preserving reasoning summaries, final answers, approvals, and user shell commands. Submitter built and tested a local prototype (Rust v0.128.0) and reported "significant visual clarity improvements." This is independent-but-convergent evidence with Claude Code's #39683/#26968: **three different tools' user bases are asking for the same "hide the mechanical noise, keep the reasoning" feature.**
- **Failure/edge-case bug — [#12278](https://github.com/openai/codex/issues/12278)**: a unified-exec command can execute successfully but *never render* in the transcript if its begin event is skipped while an unrelated "exploring" exec cell is active — described as "very misleading" since it hides ran commands from the end user. This is evidence that ad hoc grouping/coalescing logic is a source of real bugs (commands going missing from the transcript) when not carefully scoped — a caution for cxagent if it builds a similar coalescing mechanism.
- **`codex exec` non-interactive mode**: separately, Codex's headless mode streams progress to **stderr** and prints only the final agent message to **stdout** — a totally different, non-TUI approach to noise reduction (just don't render intermediate tool activity live at all). Source: [developers.openai.com/codex/noninteractive](https://developers.openai.com/codex/noninteractive).

### Amp (Sourcegraph)

- **Setting**: `amp.terminal.detailsExpandedByDefault` — boolean; controls whether "thinking and tool call details" start expanded or collapsed in the CLI transcript. **`Alt+T`** toggles collapse/expand for the current session. Source: [ampcode.com/manual](https://ampcode.com/manual) (official docs, fetched directly).
- Manual does **not** document: line-count budget, truncation behavior, failure-state rendering, grouping, or progress indicators. Flagged as a gap rather than inferred.

### Aider

- Aider is architecturally different — it doesn't have a discrete "tool call" abstraction in its default terminal UI the way agentic-loop tools do; most of its terminal output is diffs and shell-command echoes.
- `--verbose` (env: `AIDER_VERBOSE`) dumps raw wire-level request/response data; recommended combined with `--no-pretty` for debugging. Source: [aider.chat/docs/config/options.html](https://aider.chat/docs/config/options.html).
- No default truncation; a feature request (found via search, referenced from the Claude Code #26968 discussion) exists for verbose-mode MCP payload truncation but is not confirmed as implemented.

### Pi (earendil-works/pi)

- **[Issue #3114 "Feature: Collapsible tool output for non-destructive tools"](https://github.com/earendil-works/pi/issues/3114)**: complaint that long/verbose output from non-destructive tools (read, ls, grep, find, safe bash) "fill up the terminal screen, making it hard to follow the conversation" — concrete example given of a "brain-search" query producing 100+ lines of JSON that pushes earlier conversation off-screen. Proposed fix: collapse output exceeding a configurable N lines, showing only the command and a one-line summary. This is the same shape as the Claude Code / Codex asks, from a third, smaller/independent project — reinforces that this is a convergent, cross-project pain point rather than one team's idiosyncratic preference.

### Cline, Goose, OpenCode

No concrete rendering evidence (line counts, glyphs, truncation behavior, grouping, failure handling) was found via web search in this pass. I did not fabricate details for these. OpenCode's TUI is confirmed to be built on `@opentui/solid` (a Solid.js-based terminal renderer) per its DeepWiki page, but that's architecture, not rendering behavior.

## Cross-cutting findings

1. **Dominant pattern**: default-expanded-with-manual-collapse (Claude Code, Amp) or opt-in-compact (Gemini CLI's `compactToolOutput` defaults to `false`). **No tool researched defaults to collapsed/compact out of the box.** Every tool that has a compact/quiet mode makes the user turn it on — either as a settings flag or a keybinding toggle. This is itself notable: cxagent defaulting to compact would be ahead of the pack, not behind it.
2. **Line-cost**: ranges from Gemini's compact-mode goal of 1-2 lines, to Claude Code's collapsed ~2-3 lines (icon line + indented result line), up to unbounded (Pi's 100+ line JSON dump, Gemini's pre-compact verbose YAML "1,000+ lines," Claude Code's own MCP payload complaint). The verbose end is universally the complained-about state.
3. **Tool-vs-prose signaling**: glyph/icon + indentation is the most common approach where evidenced — Claude Code's `⏺`/`⎿` pair is the clearest concrete example found. Gemini CLI uses a distinct component (`DenseToolMessage` vs. bordered box) rather than just a glyph — i.e., *shape* of the block, not just a marker character, differs by tool type.
4. **Grouping**: Gemini CLI is the only tool with **confirmed, shipped** grouping logic — `ToolGroupMessage` packs consecutive "dense" tool outputs together while keeping shell-like tools in individual bordered boxes. Codex has a related but fuzzier concept ("coalesced exec/tool group" for the in-flight cell only) that has also produced a bug where commands can vanish from the transcript. No tool researched showed a "Round 2 · 5 tools" style batch/round header — that specific pattern (grouping by *agentic round* rather than by *tool type*) appears to be unaddressed in the wild, i.e. there's no prior art to copy for it, but also no evidence against it.
5. **Failure handling**: essentially undocumented across every tool researched, except negatively — Codex's #12278 shows failure/edge-case *mishandling* (a command silently disappearing from the transcript) as a real bug born from ad hoc coalescing logic. No tool was found to visibly do something special (color, expand, inline error, retry affordance) for a failed tool call in the sources gathered. This is a real gap in the prior art, not just a gap in my search.
6. **Progress indicators**: only Claude Code has confirmed evidence — a live elapsed-time counter on the collapsed one-line summary, added specifically to fix long tool calls "looking stuck." Codex's headless (`codex exec`) mode instead streams all progress to stderr, keeping stdout clean — a completely different strategy (route noise to a side channel rather than render/collapse it).
7. **User-complaint evidence is the strongest signal in this research**, and it converges hard across three independent projects:
   - Claude Code #39683 (persistent collapsed-by-default) and #26968 (MCP payload truncation)
   - Codex #21252 (hide tool activity entirely)
   - Pi #3114 (collapse non-destructive tool output over N lines)

   All three describe the *identical* failure mode in different words: **mechanical/verbose tool output burying the reasoning and prose that the user actually came to read.** This is exactly the problem statement cxagent's team lead described. None of these requests have shipped as the *default* behavior anywhere researched — Gemini CLI shipped compact mode but opt-in; Claude Code has a session-scoped toggle, not a persisted default; Codex's fix is an unmerged community prototype.

## Recommendation for cxagent

Given cxagent's three message kinds (orchestrator / worker / tool), and that no competitor has shipped default-collapsed tool rendering (this would be a genuine improvement on the state of the art, not risky):

1. **Tool calls should default to compact, not expanded.** Every piece of user-complaint evidence gathered says the current cxagent behavior (5 lines per trivial tool call) is the exact pain point real users of Claude Code, Codex, and Pi have independently filed issues about. Follow Gemini CLI's shipped pattern: one line = status glyph + tool name + one-line result/diffstat summary, with an expand affordance (not a full block) for anyone who wants detail.
2. **Differentiate tool-call shape from worker/orchestrator shape**, the way Gemini CLI's `ToolGroupMessage` differentiates dense tools from bordered-box tools — but apply that distinction at the *message-kind* level cxagent already has: `tool` → dense one-liner; `worker` → full prose block (it earned the space, per the team lead's framing); `orchestrator` → distinct from both (Claude Code's `⏺` pattern — a glyph-prefixed line for the model's own turn — is a reasonable model here, since no other tool researched clearly separates "planner turn" from "tool result" the way cxagent needs to).
3. **Group consecutive tool calls** the way Gemini CLI packs dense outputs together — this directly addresses the "six steps cost ~26 lines" complaint. Use tool-type as the grouping key (reads/searches pack tightly; a shell command with real output gets its own line or small block) rather than inventing a "round" concept nobody else has tried — there's no prior art either way for round-based grouping, so tool-type grouping is the lower-risk choice.
4. **Give failed tool calls more visual weight** — color and an inline error line at minimum. This is the one dimension where the research found no positive prior art at all (only a bug from *not* doing it, in Codex #12278), so cxagent doesn't have a pattern to copy, only a hole to avoid: make sure a failed compact line never just silently looks like a successful one, and never lets a coalesced/grouped rendering make a failure disappear the way Codex's bug did.
5. **Add a live progress indicator only for calls that are actually slow** (mirror Claude Code's elapsed-time-ticker fix) — but keep it out of the default line for the 0.0s cases the team lead cited; a fast tool call shouldn't reserve space for a timer it never needs.
6. **Do not make compact-by-default the *only* mode.** Every tool researched preserves an expand/verbose escape hatch (Ctrl+O, Alt+T, `ui.compactToolOutput`, `/focus`). Ship the dense default, but keep a full-transcript expand affordance — ideally persisted per-session at minimum, since Claude Code's own users are still asking (issue #39683, unresolved) for that expand/collapse state to survive across sessions, which cxagent could get right from day one.
