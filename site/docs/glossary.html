Glossary

The words these pages use in a sense of their own.

Each entry says what the word means here and links to where it is covered in full. The first group is for anyone using cxagent; the second is for plugins, which a user meets in the plugin manager and an author meets in the SDK.

Using cxagent

Composer

The input box at the foot of a tab, where you type a message or a /command. Enter sends it. What you type while a turn is running is queued, and Esc, which ends the turn, puts anything still queued back in the composer rather than discarding it. An agent's own tab has a composer too, and what you type there goes to that agent, not to the session. Commands →

Worker

A sub-agent: a second agent the session hands a piece of work to, with its own context, its own conversation and its own compaction. It runs, returns one report, and the parent keeps that report rather than everything the worker read. A worker runs in the foreground, with the turn waiting on it, or in the background while the conversation carries on; Ctrl+B moves one that is waiting to the background. Each has a tab of its own, and you can send it a message while it works. Its spend is counted apart from the parent's — the panel's workers line. Workers →

Task

Work running unattended: above all a long shell command that run_shell left running in the background, such as a build or a test suite. A task is a process, where a worker is an agent. The tasks panel (F7) and /tasks list both — background workers and background commands, running first, then finished — and each opens in a tab showing its output. Tasks →

Instance

One entry in config.json's providers block: a name bound to one endpoint and one model, with that model's settings — its key, its context window, its thinking level. Two instances can be the same server with different models, so switching the model and switching the provider are the same act: /model picks an instance. The configuration dialog's Providers tab lists them. Configuration →

Occupancy

How much of the model's context window the conversation fills right now: the tokens in context against the window, as in 5,725/32,000 on the status line. A worker's row shows its own. The window is the instance's contextWindow, or what the endpoint reports when that is unset; with neither, there is no denominator and no percentage is shown. Configuration →

Compaction

Summarising the conversation through the model to free room in the context, rather than dropping the oldest turns. It happens on its own when the context passes contextCompressThreshold — by default 80% of the window, when the window is known — and on demand with /compress. A worker compacts its own context, separately from the parent. The session's history.jsonl is never compacted, so an export still has everything. /compress →

Trust

Two decisions share the word. Trusting a folder is the answer to Trust this folder?, asked the first time a session opens in it: in a trusted folder, file reads and commands that only read stop asking, and in accept-edits mode — chosen with /mode edits or Shift+Tab; the default asks — so do writes inside it. Commands that can write, and anything outside the folder, still ask, and no mode can widen past that answer. /trust shows or changes it; --trust trusts a folder for one headless run without saving anything. Trusting a plugin is approving it at load, against a hash of its load set. /trust →

Plugins

Sidecar

The <name>.plugin.json file shipped beside a plugin's binary. It declares the plugin's name, version, contract, kind (managed or native), its tools and how each is gated, and any text it adds to the model's instructions. cxagent reads it before loading the binary, so the load prompt can say what a plugin claims without running it, and refuses the load if the plugin's own answer disagrees with it. The sidecar →

Gate, gated, dynamic

A gate is the permission check a tool call passes before it runs. A plugin's tool declares its gate in the sidecar: "gated": true asks before every call (and offers Always unless the tool also says "alwaysAskable": false); false never asks; "dynamic" hands each call to the plugin, which looks at the arguments and either lets it through or asks with wording of its own. The sidecar is a ceiling: code cannot quietly turn a true into no prompt. A tool embedded through CxAgent.Core passes two gates — one for the tool in this folder, then its own per-call check. Permission →

Load set

Every file a plugin load would bring in: the binary, its sidecar, its README and whatever else is in the plugin's folder. The load prompt shows one hash over the whole set, and that hash is what you approve; change a byte of any file in it and the question comes back. Nothing in config.json can pre-approve a load set. Trusting a plugin →

Shape

Used in two places, both meaning form rather than content. A catalog entry's shape follows the plugin: a managed plugin has one download for every platform, a native one a download per platform, and an entry hosted elsewhere commits its own sha256 where one released with cxagent leaves it to the release to stamp. plugin verify holds an entry to its shape. And the static safety check on shell commands refuses on shape — a redirect, a chain — rather than on danger, which is why dotnet build 2>&1 | tail asks. Publishing →

Catalog

A catalog.json listing plugins: each one's version, platforms, publisher, licence, download address and sha256. cxagent's own is generated from plugins/plugins.json at release and published beside the plugins page; the plugin manager (F2) reads it, and every download is checked against its hash before anything is written.

Store

A catalog of your own: a catalog.json and the zips it points to, served from any static host. cxagent store build makes both from a folder of built plugins. /plugin store add <name> <url> adds one to a machine, after which its plugins appear in the plugin manager beside cxagent's and install with /plugin get <store>/<plugin>.
